# ZUDO SMM PANEL

A complete, single-origin Node.js application: responsive customer workspace, separate owner console, PostgreSQL wallets and sessions, live provider integration, verified UPI deposits, and Render configuration. No frontend-only demo and no runtime dependency on local files.

## Deploy: GitHub → Render → secrets → live

1. Extract the project ZIP. Upload the **contents** of the extracted project to your GitHub repository. `render.yaml`, `package.json`, `package-lock.json`, `src/`, `migrations/`, and `public/` must be at the repository root. Include dotfiles and the `.github` directory; do not upload the ZIP itself as the application.
2. In Render, choose **New → Blueprint**, connect your repository, and use the root `render.yaml`. Render provisions the Node web service and PostgreSQL database and wires `DATABASE_URL` automatically.
3. Enter **OWNER_PASSWORD** and **SMM_API_KEY** when prompted. Use the exact owner password and real API key you supplied in the project request. They are deliberately **not committed** in this repository. `OWNER_USERNAME=zudo` and the exact provider endpoint are already configured as environment variables. Render generates `SESSION_SECRET` automatically. You may replace that with your own 32+ character random secret.
4. Apply the Blueprint / deploy. Build command: `npm ci && npm run build`. Start command: `npm start`. Startup runs locked, transactional migrations and provisions the owner before opening the HTTP port. Repeated deploys do not reset balances or reset the markup.
5. Open your Render URL. Customer registration: `/register`. Customer login: `/login`. Owner login: **`/owner-login`**. Health check: `/health`.

No source edits are required. Render sets PORT. The Blueprint uses paid compute plans (web `0.5c-512mb`, PostgreSQL `0.1c-256mb`); check Render pricing before applying it. Keep both resources in the same region. If you prefer to create a Web Service manually instead of a Blueprint, use the same commands, set every required variable listed below, and supply the Render database internal connection string as DATABASE_URL.

Copy .env.example only for local development; set real values in your untracked .env. Never upload .env, database URLs with passwords, private TLS keys, or production credentials to GitHub. Secrets are passed solely in server-side provider requests. Logs do not print provider keys.

### PostgreSQL connection notes

DATABASE_SSL=auto uses Render's private/internal connection without TLS when the hostname is an internal short name or ends in .internal; localhost is treated the same way. Public/external database hosts use TLS with certificate verification. Render documents internal TLS as optional and external TLS as required. Use the Blueprint-generated internal DATABASE_URL on Render. Do not disable certificate verification globally. If your organization requires encrypted internal database transport, use a verified external connection or a network/TLS configuration appropriate to its certificate policy. The default private-network connection is compatible with the generated Blueprint.

## Implemented functionality

Customer: registration, login/logout, password changes, per-account dashboard, live searchable/category-filtered services, descriptions and limits, server quotes, orders, status refresh, automatic background status checks, wallet, UPI deposit requests, ledger/history, support tickets and replies, profile.

Owner: separate role-gated login, real database statistics, provider balance, user search, independently paginated user order and transaction histories, suspend/restore, separate **add balance** and **deduct balance** forms, confirmed atomic adjustments, deposit approve/reject, configurable markup, all orders/provider IDs/cost snapshots, uncertain-order reconciliation, support replies/closure, and audit logs.

The default **60% markup** means provider cost ₹100 → customer charge ₹160. This is markup on provider cost, not a 60% gross margin. Changes apply only to future orders. Rates are per 1,000 except Package services, which are one-time rates. Decimal.js performs server-side arithmetic; customer charges round upward to a paise and proportional refunds round down to avoid over-refunding. The example ₹100 → ₹160 is exact.

## Provider integration and documented limits

Documentation reviewed: https://mysmm.org/api

Backend HTTP POST requests use application/x-www-form-urlencoded with key and action. Implemented application actions: services, balance, add, status. Production uses the exact URL specified above; the test suite alone uses a local isolated provider fixture. There are **no fake provider responses in production**.

The complete returned catalogue is cached dynamically in PostgreSQL and refreshed after five minutes or by owner action. No service IDs, rates or catalogue entries are hardcoded in production. The frontend does not receive the API key. An INR balance/currency check is required before order submission.

Documented checkout types supported: **Default** (service, link, quantity), **Package** (service, link), and **Mentions Media Likers** (service, link, quantity, media). Optional Default drip-feed parameters are not exposed by this UI. The provider's live catalogue also returned **Subscriptions**, but its public add-order documentation does not publish a subscription contract or recurring-cost policy. Those entries are displayed and explicitly marked unavailable for checkout; this implementation intentionally does not invent recurring billing or silently bill a subscription as a one-off order. Obtain an authoritative provider contract before adding subscription checkout. This is a known scope limitation, not a claim of complete subscription support.

Provider descriptions are displayed as escaped plain text. If the provider does not supply a description, the UI says so rather than inventing one. Provider errors are surfaced safely, with explicit rejections distinguished from uncertain HTTP/network responses.

### Avoiding duplicate paid orders

The browser generates an order UUID, reuses it across transport retries, and the database enforces uniqueness per user. Wallet reservation and order creation are one transaction. The provider add call is issued at most once by that accepted request. The provider does not document client-supplied idempotency or lookup by client reference, so a provider timeout cannot safely be automatically retried.

- Explicit provider JSON rejection: mark Failed and atomically refund the full reserved charge.
- Timeout, malformed response, interrupted process, or uncertain database/provider result: keep the reservation and mark **Needs review**. Do not submit the same purchase again under a new UUID.
- Owner checks the provider's own order history, then attaches the verified provider ID, or confirms that no order exists and refunds. Both require confirmation, a reason and an audit entry. The application cannot independently prove that a manually entered provider ID belongs to that original submission; this is an owner reconciliation responsibility.
- Worker checks active order statuses every minute, at most 30 orders per sweep. A PostgreSQL advisory lock prevents duplicate workers. Larger installations should use a dedicated queue and adapt provider throughput limits. Never run multiple independent order-submission retry workers against this API.
- Completed/canceled/partial final states are not regressed by stale refreshes. Canceled orders are refunded fully; partial orders proportionally to undelivered quantity. Customer refunds and ledger entries are idempotent. Actual provider refund settlement must still be reconciled in the provider account.

Net revenue is order charges less customer refunds. Provider costs/profit in the owner overview are explicitly **estimates based on order cost snapshots and proportional refunds**, not bank settlement or audited financial accounts. Actual provider charges are stored when returned by status and can differ from snapshots. No external fees, taxes, chargebacks or FX conversion are inferred.

## Payment verification and wallet safety

This is a **manual UPI verification workflow**, not an automated bank/UPI gateway. Users pay externally and submit a UTR and amount. Submission alone never credits funds. An owner must independently verify settled receipt and exact amount in their bank or UPI statement before approving. The app cannot verify bank settlement itself. Rejection never credits funds.

UTRs are normalized to uppercase and globally unique. Approval takes a row lock, requires pending status, credits the locked wallet and writes its ledger/audit records in one transaction. Concurrent/repeated approvals cannot double-credit. Wallet debits use database row locks and a nonnegative balance constraint. All mutations preserve transaction history and require server authorization. Adjustments carry UUID operation references to prevent duplicate credits/debits on transport retry.

## Security model

Bcrypt-compatible bcryptjs hashes with cost 12; 10–72-byte passwords; normalized unique usernames; PostgreSQL session store; session regeneration at authentication; role checks against the current database user on every request; suspension enforcement; password-change session invalidation; 8-hour sliding session expiry; __Host- secure HttpOnly SameSite=Lax cookies in production; session-bound CSRF tokens; origin verification on configured domains; Helmet/CSP/HSTS; login and API rate limits; Zod validation; parameterized SQL; escaped user/provider text; server-only prices; transactional ledger and audit logs.

Render is a trusted single reverse proxy; the Express trust-proxy setting matches that deployment. Do not expose this origin directly behind an arbitrary untrusted proxy. Rate limiting uses the process-local limiter store (wallet data and sessions do not): this is suitable for the single-instance Blueprint. Add a shared Redis limiter before horizontal scaling, use a single web instance for the supplied deployment, configure database backups, monitor provider errors and pending-review orders, and use a strong owner password. Security measures do not constitute a third-party penetration test or a guarantee against every threat.

Changing OWNER_PASSWORD in Render and restarting synchronizes its bcrypt hash and invalidates sessions tied to the old hash. Owner password changes are intentionally not accepted from the browser. OWNER_USERNAME is provisioned once; do not change it after provisioning without a controlled account migration. Changing secrets is environment configuration, not source editing.

## Local development and tests

Use Node 22 and PostgreSQL 16 or newer. Install dependencies with npm ci. Set DATABASE_URL, OWNER_USERNAME, OWNER_PASSWORD, SESSION_SECRET and SMM_API_KEY in your untracked .env. Set NODE_ENV=development for ordinary HTTP localhost cookies, then npm run migrate and npm run dev. Production runs npm start, which performs migrations automatically.

### Integration suite (destructive on its dedicated test database)

Create a separate empty PostgreSQL database with **test** in its name. Set TEST_DATABASE_URL to that database, then run npm test. The suite refuses to run without an explicit test URL and **drops/recreates its public schema**. Never point tests at a production database. Tests use isolated credentials and a local HTTP provider fixture; they do not spend provider balance. No fixture is loaded by production.

### Browser verification

npm run test:browser expects a local verification deployment at TEST_BASE_URL (default https://localhost:3443), with the owner credentials in OWNER_USERNAME/OWNER_PASSWORD. Install Chromium using npx playwright install --with-deps chromium. For production-cookie verification, use a local HTTPS reverse proxy forwarding X-Forwarded-Proto: https to the production server; allow the self-signed certificate only in the local test browser. TEST_BASE_URL is restricted to localhost/127.0.0.1 to prevent accidental test mutations on a public deployment. The test creates local-only users, test UTR requests, support messages and owner wallet adjustments; it submits **zero paid provider orders**. Artifacts go to TEST_ARTIFACT_DIR (or the local verification output directory). Use a throwaway local database, never real customer data.
